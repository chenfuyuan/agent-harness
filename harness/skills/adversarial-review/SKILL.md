# 零上下文对抗审查（Adversarial Review & Builder Check）

编写方案或代码的同一个对话窗口存在严重的“思维顺从惯性”。本技能强制拉起**无历史包袱的独立只读子代理**（必要时调用异构模型 CLI）扮演挑剔的外部审查员。

## 关卡 A：开工前挑刺（Pre-Build Builder Check）

在 `slice-NN.md` 准备切入 `Mode: build` 前，派一个**全新只读子代理**使用以下提示词审查：

```text
你是一名兼具深厚领域知识与洁癖级工程标准的首席架构师，只拿到了仓库里的设计文件，无法向原作者脑补背景。
请依次读取：design/SYSTEM.md、design/TECH.md、design/DESIGN.md、母仓 harness/playbooks/INDEX.md、当前切片文件 <slice-path>，以及涉及模块的 src/*/AGENTS.md 与 design/prototype/ 相关文件。
只报告动工前必须澄清的硬伤：
1. 领域与业务死穴：是否存在违背该领域底层常识、业务不变量或数据因果律的隐性漏洞、数据正本归属空白或高危异常分支缺失；
2. 代码架构腐化风险：本片方案是否破坏 TECH.md 的单向依赖分层（如把业务逻辑漏进 UI/Infra）、违背持久化表“只加不删”兼容铁律，或把应做成确定性状态机/同构纯核的逻辑写成面条胶水；
3. 不得不猜且猜错必返工的契约矛盾。
跳过明确标为“开发自决”的细枝末节与文案措辞。若无硬伤，直接回复“无阻塞问题”。
```

- **结果分流处置**：
  1. 底稿或原型里已有答案只是没写清 → 主代理直接补齐文件，不打扰用户；
  2. 不影响用户感知与安全/数据一致性的实现细节 → 主代理定默认值写入切片单；
  3. **真正影响业务结果或风险边界的漏项** → 按优先级逐个带回主对话请用户拍板（默认每轮聚焦 1 个最关键问题，仅强耦合项最多合并 2 个）。

## 关卡 B：交付前零上下文 Diff 审计（Pre-Delivery Diff Audit）

在切片准备向用户报完工前（确认 `scripts/check` 已返回 `0` 后），派一个**从未参与本次编码的全新只读子代理**审查：

```text
你是一名严苛的代码安全与架构审计员。请读取 design/SYSTEM.md、涉及模块的 src/*/AGENTS.md、当前切片单 <slice-path>，并运行 `git status -sb` 与 `git diff HEAD` 审查本次实现（新增未跟踪文件 ≤400 行直接读取，>400 行大文件先用 `ws map <file>` 看骨架后按行段精读）。
重点揪出以下 7 类问题（忽略 2px 样式微差等外观琐事）：
1. 假实现与偷懒：表面接通但分支硬编码假数据、静默吞掉错误、跳过必要校验；
2. 破坏骨架与不变量：违反 SYSTEM.md 数据正本归属、`.harness-rules.json` 分层边界，或违背模块 AGENTS.md 中的精度/幂等/边界禁令；
3. 危险边界漏判：外部 API 超时/报错、空数据、重复点击、极端数值下是否会导致状态损坏、越权或不可逆外部副作用；
4. 规模增长后的读/写放大暗雷（对照 F05）：扩展自建表或高频过滤列缺索引、分区分批写入缺有界增量合并、读接口无界整表拉取长文本、不可变快照缺水位缓存或返回可变引用、前端路由漏懒加载或隐藏 Tab 偷跑重查询；
5. 密钥与越权隐患；
6. 变更半径越界与消音作弊（Scope Hygiene）：是否顺手重构了切片范围外的无关文件/公共配置、放宽类型/删改既有断言，或滥用 `rule-ok`/`ignore-ok`/`stub-ok` 绕过确定性护栏；
7. 威胁模型对齐与反过度工程（对照 F08）：严格按真实影响分级——仅「绕过后会静默自动执行、破坏权威正本、突破正向白名单/OS 边界或导致未授权高危操作/权限越界」才标 `Blocker`；若已落在**人工确认门禁且禁止持久化**的分支里，仅标 `Warning` 并建议文档写清边界，严禁按 CTF 红队标准逼主代理手写图灵完备语法解析器。若发现某文件因打地鼠补丁畸形膨胀背离 `SYSTEM.md` 定位，直接报架构异味喊停。
仅输出带文件路径与行号的确切缺陷分级（Blocker / Warning）；若无实质缺陷，输出“审计通过”。
```

### 审计熔断闸门（Audit Circuit Breaker，对照 F08）
零上下文审查**默认 2 轮收敛，硬上限 3 轮**。命中以下任一信号时，**严禁默默拉起下一轮重审**，必须立刻停手向用户汇报架构复盘与替代方案（换正向白名单 / 换 OS 级沙箱 / 诚实校准威胁边界）：
1. 同一模块连续 **2 轮**仍不断冒出新 `Blocker`；
2. 因修审查项导致单文件净增超过 **+300 行**，或文件体量畸形膨胀背离 `SYSTEM.md` 定位；
3. 新报 `Blocker` 落入「用应用层黑名单解析器对抗 Shell/SQL/正则/HTML 等图灵完备混淆」的打地鼠区间。

### 关键模块可选增强：异构模型交叉互审（写的那一家不审自己）
当切片涉及**不可逆外部副作用、核心安全闸门或权威数据正本迁移**时，若本机已安装另一端 CLI（如当前在 `agy`/Claude 下可调 `codex exec --sandbox read-only`，或在 Codex 下调 `claude -p`），可将上述审计提示词交给异构模型对 `git diff` 再过一遍筛，两家均无 Blocker 后再交付用户真用。

## 关卡 C：故障修复治本审查（Bug-Fix Cure Audit）

在任何故障/Bug 修复分支（`fix-*` 或排障开发线）准备合入前，派一个**从未参与本次排查与编码的全新只读子代理**对照「治本四校」审查：

```text
你是一名严苛的故障修复与可靠性审计员。请读取涉及模块的 src/*/AGENTS.md、母仓 harness/playbooks/INDEX.md（及命中的错法卡），并运行 `git status -sb` 与 `git diff main`（或 `git diff HEAD`）按行段精读本次修复代码与回归测试。
专门揪出以下 4 类“症状消音浅补丁（Symptom Silencing）”（任中一条即标 Blocker）：
1. 降底线洗白异常：是否靠扩宽权威正本字段、放宽枚举/校验规则、塞假默认值、删改已有断言，或仅改 AI 提示词而无 100% 确定性代码护栏来让报错消失？
2. 毁灭审计现场：拦截或降级异常时，是否在校验前提前截断输入、丢弃或吞掉完整原始异常上下文，导致事后无法查账？
3. 缺失舱壁隔离：单条或单篇损坏数据被拒绝后，是否可靠标记为 failed/rejected 隔离，确保同批正常数据与下游同步继续推进而不连坐崩盘？
4. 无终止重试与级联副作用：同输入必复现的确定性失败是否按输入/版本水位锁死零重复重试（严禁用固定 sleep/cooldown 伪装止损）？只读查询接口是否残留未加水位幂等锁的写副作用？
仅输出带文件路径与行号的确切缺陷分级（Blocker / Warning）；若完全满足治本标准，输出“治本审计通过”。
```
