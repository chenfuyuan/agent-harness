# AI 原生垂直切片开发闭环（Slice Plan & Build）

面向 AI 智能体上下文特性设计：用**声明式代码护栏（`.harness-rules.json`）**与极薄模块备忘打造“垃圾代码活不下去”的确定性花园，用**信任阶梯双车道（`full` / `fast`）**按风险分配验收仪式，确保每一片做完立刻进入真实日常使用。

## 1. 信任阶梯双车道与开工前门禁（严禁新功能单方案抢跑）

先按任务风险走 **信任阶梯双车道** 分流（高风险绝不降档，低风险绝不走重仪式）：

- **快车道（`--lane fast`）**：仅限**纯内部重构、补单测/属性测试、收紧 `.harness-rules.json` 规则、或局部确定性小 Bug 治本修复**（严禁新增 UI 页面、破坏数据正本迁移或改动不可逆高危核心规则）。跳过多方案比选与 HTML 截图仪式，直接运行 `<Hub-Ref>/bin/ws line new <slug> --lane fast [--scope <独占目录>...]` 开线编码，仍强制过全量 `scripts/check` + 零上下文审查 `0 Blocker`，最后给用户一屏验收摘要确认后收尾。
- **重验收档（`--lane full`，默认）**：适用于**新功能切片、UI 交互变更、权威数据正本或不可逆高危规则改动**。哪怕 `design/SYSTEM.md` 已有宏观大纲，**严禁把 AI 当成照单抓药的功能翻译机直接写死单一方案或抢跑开线**：

1. **先明需求再多方案比选（Step 0 · 禁抢推方案，必先停下等用户选）**：
   - **⓪ 模糊需求前置对齐（问题空间）**：若用户抛出的是一句宽泛或带不确定性的新功能想法，**严禁直接端出完整方案并贴「推荐」标签**；先通过逐轮单点追问（默认每轮只问 1 个最关键问题，必要时附 1 行议程路标，严禁问卷式连发多题）对齐真实使用场景、核心边界、验收期望与外行易忽略的领域硬律（Unknown Unknowns），需求边界清晰后再出方案。
   - **① 领域专家视角点破隐性暗坑**：结合既有 `design/SYSTEM.md`、`design/TECH.md`、`src/*/AGENTS.md` 与 `<Hub-Ref>/harness/playbooks/INDEX.md`，主动识别需求背后最易踩死的 **2–3 个领域与工程死穴**（例如数据口径与时间线因果一致、异步并发幂等竞态、多工作树共享库迁移兼容等），客观审视前提假设。
   - **② 第一性原理构想 + 业内实践照妖镜（只作参考、绝不直接套用）**：先从本项目实际情况与既有底座出发推导原生解法，再针对所属细分领域检索 2–3 个公认标杆开源项目或成熟工业范式做**查漏、破惯（剥离重型包袱）与局部采珠**，严禁直接照抄或跨领域套用无关套路。
   - **③ 提出 2–3 套「业务范围 × 代码架构」协同方案（拒绝凑数假选项）**：在对话正文清晰呈现 **2–3 套贴合本项目实际且真正成立的差异化方案**（**默认亮明推荐方案、核心推荐原因，并必须同时写明「什么前提下不该选它」**，防止盲从），每套方案必须同时讲透：
     - **业务闭环与厚薄切法**（每片控制在 **3–6 个原子步**，优先切每天高频用 + 验证最危险假设的主干，明确本片做什么与延后什么）；
     - **代码与数据架构映射**（如何落入 `domain/` 纯计算核/状态机 ↔ `app/` 编排 ↔ `infra/` 外部适配与只加不删表迁移，核心不变量与容错降级边界）；
     - **利弊取舍与演进代价**（复杂度、性能、后续扩展弹性对比）。
   - **④ 硬性停顿等待用户选择**：**输出多方案对比后当轮必须到此停下（若先落盘提案草稿，切片状态须标为 `proposed`），严禁在同一轮未获用户选择前顺手执行 `ws line new` 或编写业务代码！**
2. **用户选定后的定稿、挑刺与开线分流**：
   - 待用户明确回复选定方案（或组合微调）后 → 按 [templates.md](./references/templates.md) 将选定方案、核心代码架构与取舍理由落盘至 `design/slices/NN-<slug>.md`，将切片状态更新为 **`approved`** → 调用 `adversarial-review` 做开工前挑刺（Builder Check，核对 `SYSTEM.md` + `TECH.md` 零硬伤） → 按阶段分流：
     - **首片地基 `Slice 00`（仓库尚无初始提交）**：在主目录运行 `<Hub-Ref>/bin/ws mode build --slice design/slices/00-foundation.md` 落地全栈底座；验收通过并经用户确认完成**首次基线提交（Initial Commit）**后，将主目录切回 `ws mode design` 守门。
     - **后续切片 `Slice 01+` 与多需求并行（默认开线，`ws line new` 硬校验 `approved` 状态）**：主目录保持干净 `Mode: design` 只做设计与合并；运行 `<Hub-Ref>/bin/ws line new <slug> --slice design/slices/NN-<slug>.md [--scope <独占目录>...]`（若项目自带 `scripts/line` 则优先用项目脚本；**若切片缺失或仍为 `proposed/draft` 未拍板状态，`ws line new` 将硬性拦截开线**），自动在 `../<项目>-lines/<slug>` 创建 `line/<slug>` 工作树、迁入未入库切片单保持主仓干净、软链 `.env` 与三端门禁钩子并写入工作树本地 `Mode: build`。多线并行期间可用 `ws line list` / `ws line check` 检查文件碰撞。

## 2. 首次进入 Build 必做：`Slice 00`（架构守卫落地与日常真用入口）

新仓库第一次进入 `Mode: build` 时，先将 `design/TECH.md` 的工程架构转化为可运行的地基与自动化门禁，严禁把部署与分层守卫留到几周后：

1. **工程骨架与声明式硬护栏兑现**：若为 L1 轻量工具尚未建 `TECH.md`，先补齐精简版 `design/TECH.md`；按 `TECH.md` 建立单向依赖目录分层（如纯计算 `domain/` 与 `infra/` 物理隔离），并将首批**公开入口（`public_entries`）、单向分层禁令（`layer_bans`）与高危 API 封禁（`pattern_bans`）**直接写入项目根 `.harness-rules.json`（见 [templates.md](./references/templates.md)），交由 `ws check` 自动执行。
2. **三件套脚本与零容器云端节流到位**：
   - `scripts/dev`：一键启动应用；接入 `<Hub-Ref>/bin/ws line env`，在并行开发线运行时自动使用槽位偏移端口（`BASE + slot`）与独立容器项目名 `<proj>-<line>`（容器/卷统一打标 `ws.repo=<proj>`、`ws.line=<line>`），默认共用主开发环境真实数据（配合**持久化表结构只加不删**铁律，1 秒开线免空库盲测）；
   - `scripts/check`：一键串联项目纯内存单测/集成测试 + 架构分层守卫（含纯内存单测禁连 DB/嵌入式数据湖）+ `<Hub-Ref>/bin/ws check`（全量入口先查 `--full-covered` 跨工作树复用已验凭证、`--force` 强制重跑，全量通过后 `--record-full` 签发凭证；配 `--ff --maxfail=10` 与剖析开关；打版本/发布脚本前置 `--verify-full HEAD` 锁死未验代码）；
   - **云端 CI（若配置 `.github/workflows/check.yml`）**：严格遵循 [templates.md](./references/templates.md) 的**“本机全量凭证 + 云端 <1 分钟零容器底线”**模式，仅在 `push tags: ["v*"]`、`pull_request`、`workflow_dispatch` 触发并开启 `concurrency` 取消旧跑，**严禁在 `push: branches: ["**"]` 上重复跑重型容器测试双倍消耗免费配额**；
   - **日常真用入口打通**：把用户本机每天打开它的真实方式（Docker Compose / 本地常驻服务 / 快捷命令）当场装好跑通。

## 3. 每个业务切片的五步 AI 原生执行与真人验收流

### Step 1：切片技术方案设计与真数据探针（Slice Tech Design & Spike）
- **严禁照着原型图直接翻译面条代码**：涉及状态机、算法、并发流或数据管道的切片，动刀前必先对照业内成熟工程做法、`design/TECH.md` 及 `<Hub-Ref>/harness/playbooks/INDEX.md` 高频错法索引，在 `slice-NN.md` 写明**本片核心数据结构、状态转移/幂等规则与异常降级策略**。
- **真数据探针隔离试错**：涉及真实接口、外部协议或历史样本数据时，经用户授权环境配置后，**派独立子代理**编写临时探测脚本跑通真实请求。子代理试错日志不进主上下文，仅将**跑通的真实请求/响应 JSON 样本与字段坑点**写回当前 `slice-NN.md`；若发现真数据推翻原架构假设，立即暂停编码向用户汇报调整。

### Step 2：极薄模块备忘 `src/<module>/AGENTS.md`（按需 ≤20 行）与漏斗式定位
- 公开入口、跨层依赖与高危 API 禁令统一写入项目根 `.harness-rules.json`（唯一事实源）；**简单模块不再建 `AGENTS.md`**，仅复杂核心业务模块按需放一份极薄 `src/<module>/AGENTS.md`（格式见 [templates.md](./references/templates.md)，建议 ≤20 行 / 硬上限 25 非空行），只写机器静态规则拦不住的 **纯业务不变量与单模块测试命令**。源码文件顶部只写 1–2 行职责与隐性契约，**严禁手写函数清单或行号目录**。
- 摸底存量模块优先运行 `<Hub-Ref>/bin/ws map <dir|file>` 获取实时 AST 符号与 `[Lstart-Lend]` 行号后并行按段精读；跨目录盲找 >8 个未知文件派只读子代理（单子代理 ≤15 文件），即将修改的代码须由主会话亲读原文；若会话经历过自动压缩，编辑前先重读目标位置上下 30 行。
- `harness_guard.py` 强制守护模块 `AGENTS.md` ≤25 非空行、`.harness-rules.json` 全量硬规则、全仓禁裸类型/Lint 消音（`@ts-ignore` / `# type: ignore` / `# noqa`）与过期 `stub-ok` 占位债拦截。

### Step 3：原子实现（手算 TDD + 属性测试 + 最小改动纪律）
- **计算与状态机“手算 TDD + 属性自验证”**：
  - 凡涉及高精度数值核算、权限与安全边界、规则评分、时间窗口过滤的代码，**先用手算具体输入输出写测试并确认红灯失败**，再写实现跑绿；
  - 凡涉及**核心状态机（FSM）、守恒/边界不变量、幂等重入或可逆编解码**，优先补写**随机操作序列属性测试（Property-Based Testing）**（项目已装则用 Hypothesis / fast-check，未装新三方库时用纯标准库固定种子随机循环验证不变量），把 Token 砸在让 AI 自己撞墙找边界 Bug 上。
- **最小改动纪律（Scope Hygiene）**：严禁顺手重构当前切片/开发线范围外的无关文件、格式或公共配置；遇到类型或 Lint 报错必须修根因，严禁塞裸消音注解偷渡过检。
- **前端务实还原（零像素警察）**：
  - 真实前端工程直接 `import` 原型定稿的 `tokens.css` 变量体系，对照 `design/DESIGN.md` 与原型的 `data-component` 结构拆分为正式组件并绑定真实状态（正常态 / 空态 / 异常态）；
  - **不花时间纠结 2px 字号或微弱色差**；浏览器冒烟只验证 **零 JS 报错、主流程按钮与数据流点得通、无元素严重破版遮挡操作**。
- 每完成一个原子步，跑绿 `scripts/check` 后做一次小颗粒度本地整理（仅在用户要求或进入收尾流转时执行 `git commit`）。

### Step 4：零上下文对抗审查与分车道真人验收（严禁提前合入 `main`）
- **通用前置红线（`full` 与 `fast` 均必过）**：本机 `scripts/check` 返回退出码 `0`（零裸消音、零分层/禁式越界、零未备案占位与过期 `stub-ok`），且调用 `adversarial-review` 派零上下文子代理审 `git diff` 达 `0 Blocker`（**严守 F08 审计熔断闸门**：默认 2 轮收敛、硬上限 3 轮；同模块连爆或单文件补丁膨胀 >300 行立即停手升级架构复盘，禁机械死循环）。
- **分车道验收交付**：
  - **重验收档（`--lane full`）**：
    1. 在当前开发线运行 `./scripts/dev` 拉起独立预览服务，实测健康检查与核心页面截图（零控制台报错、空库/真数据诚实展示、挑关键数值代码外独立重算对账）；
    2. 基于 `<Hub-Ref>/harness/templates/acceptance-report.html` 在主目录生成 `docs/acceptance/<日期>-<线名>/report.html` 并 `open` 弹浏览器（含预览链接、亲手点按步骤、逐场景截图与对账、代码评审摘要与**拟沉淀草稿**），将切片状态标为 `pending-acceptance`。
  - **快车道档（`--lane fast`）**：免 `dev` 截图与 HTML 报告，在对话正文输出**一屏精炼验收摘要**（改动范围、门禁与属性/回归测试实测结论、零上下文审查 `0 Blocker` 摘要、拟沉淀规则草稿），等待用户回复确认合流。
- **硬性刹车铁律**：**在用户明确回复确认（「验收通过」或确认合流）之前，严禁运行 `ws line distill`、`ws line sync` 或 `ws line rm`，确保 `main` 分支 100% 只包含真人确认代码！** 若用户提出调整意见，直接在当前开发线修改。

### Step 5：真人确认后一键收尾（沉淀 `distill` → 合入 `sync` → 收线 `rm`）
- 待用户明确回复「验收通过」后，严格按以下物理顺序闭环：
  1. **落盘沉淀与复盘**：在当前开发线按 `compound-learn` 写入经用户确认的经验条目（融合审查拦截项 + 真机验收反馈），回填 `slice-NN.md#4 真用复盘` 并将切片状态标为 `verified`（正式环境投入日常使用后升 `used`），清理临时复现脚手架并完成提交；
  2. **锁死沉淀凭证**：运行 `<Hub-Ref>/bin/ws line distill`（若项目自带 `scripts/line` 则用项目脚本），自动执行 `ws learn check` 并将当前分支 `HEAD` 记入 `distilled_head`；
  3. **快进合入与收线**：运行 `<Hub-Ref>/bin/ws line sync`（硬门禁核验 `distilled_head == HEAD` 后变基过检快进合入 `main`），最后切回主目录运行 `<Hub-Ref>/bin/ws line rm <slug>`（自动销毁该线预览容器/网络/开发镜像并清理工作树）。
