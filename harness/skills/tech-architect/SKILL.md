# 代码与数据工程架构探索（Technical & Code Architecture）

产品标杆只教“界面怎么摆”，代码架构标杆才决定“系统稳不稳、数据脏不脏、能不能演进”。本技能在业务设计与编码实现之间建立专门的**工程架构探索关卡**，向该领域全球成熟的工程范式与标杆开源项目取经，并将结论编译为可执行的代码契约。

## 1. 规模自适应分流（防过度设计）

动手调研前先锚定项目的真实运行规模（如个人单机自托管 vs 多人协作 SaaS），**严禁把简单工具吹成分布式微服务怪兽**：

- **L1 轻量单功能工具（低状态/无复杂并发与回溯）**：跳过外部源码深挖，当轮明确薄目录分层与存储格式，写 ≤40 行精简 `design/TECH.md`，直接交棒 `slice-build`。
- **L2 / L3 核心业务系统（含实时流状态、多源数据管道、回测仿真、复杂事务或高可靠网关）**：走下面完整的三步工程架构探索。
- **存量仓库扩展**：必先跑 `<Hub-Ref>/bin/ws map <dir>` 与精读既有 `design/TECH.md`，新模块架构须融入现有分层守卫，不造割裂的“国中之国”。

## 2. 业内开源代码架构深挖与轻量化提纯

需要外部调研时，检索同技术子域的成熟工程方案并立即落盘 `design/research/tech-<topic>.md` 释放主会话上下文：

1. **拆解开源名作的“代码骨架”而非宣传软文**：针对本系统的核心技术难点（如高频流状态同步、防未来回测、多源数据清洗、崩溃恢复、插件沙箱），挑选 2–3 个业内公认标杆开源项目或经典工程架构，重点拆解其：**数据存储分层、核心领域抽象与状态机（FSM）、并发/异步边界、容错与对账机制**，标注 `[官方文档/源码]`、`[工程实践复盘]`、`[AI推导-待验]`。
2. **只学代码内功，不背大厂运维包袱**：强制剥离脱离当前规模的重型分布式基建（如单机日均百万行以内严禁盲目引入 Kafka / Flink / K8s 多服务编排），将其内核思想提纯为**轻量进程内架构与存储分层**。
3. **高发工程架构模式核对**：若系统涉及 **易过期/多源数据治理与回测、仿真与生产双模运行、实时增量流状态维护、外部不可逆写操作幂等对账、跨端接口契约或复杂算账内核隔离**，必读 [engineering-patterns.md](./references/engineering-patterns.md) 对应模式卡。

## 3. 技术单向门拍板与三层契约固化（防八股文腐烂）

1. **只为技术单向门出题**：每次聚焦 1–2 个难返工的底层决定（如：数据管道采用铜·银·金奖章分层还是单表、核心引擎采用事件驱动还是请求响应式、存储选型与进程拓扑），在正文讲清业内最佳实践与当前规模下的取舍，推荐置顶，等用户确认。框架小版本、内部工具库等双向门直接给经过验证的合理默认。
2. **拒绝长篇观赏文档，结论直接编译进三处硬约束**：
   - **`design/TECH.md`**：按 [tech-template.md](./references/tech-template.md) 固化一页硬核架构底座（控制在 100 行内：技术栈、数据分层流向、核心状态机与不变量、验证策略、标准门禁命令）；
   - **声明式硬护栏（`.harness-rules.json`）**：在 `Slice 00` 直接落盘项目根 `.harness-rules.json`（`public_entries` 模块唯一入口、`layer_bans` 单向分层与 I/O 禁令、`pattern_bans` 高危原生 API 封禁与白名单封装目录），交由 `ws check` 原生强执，免重复手写样板脚本；
   - **验证策略与交棒 `slice-build`**：明确 `domain/` 纯计算核与状态机采用“手算 TDD + 随机序列属性测试（Hypothesis / fast-check 或纯标准库随机种子循环）”，并将复杂算法下放至各垂直切片落地。
