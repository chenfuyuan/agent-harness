# 领域探索与宏观架构（Explore & Architect）

陪用户在探索中真正看懂领域本质、厘清真实需求，再从第一性原理出发并结合实际情况收敛系统骨架（`design/SYSTEM.md`），为原生原型（`bespoke-prototype`）与工程架构（`tech-architect`）提供可靠底座。

## 1. 起步分流（Scale-Adaptive Triage）

动手前先判断复杂度与存量代码环境，**严禁对小需求硬套重流程**：

- **存量代码检测（Brownfield vs Greenfield）**：若仓库内已存在 `src/`、`app/` 等生产代码，必先派只读子代理盘点现有数据正本、公共服务与技术栈约束（先跑 `<Hub-Ref>/bin/ws map <dir>` 提取 AST 符号骨架再按行段精读；若跨多个子系统，按目录拆分为单次 ≤15 个文件的窄边界子代理，防子代理自身触发压缩，只回传结构化结论与 `文件:行号`），确保新设计与既有底座同构。
- **存量平台泛化度核对（防单策略文档误剪通用底座）**：在存量底座上收到用户贴入的**单一方法论/单一策略/单一场景规格书**（哪怕原文档内写有“砍掉/停用其他模块”等激烈措辞）时，提议裁剪存量通用模块前必须作为单向门向用户核实：**这是系统的唯一永久形态，还是通用多场景底座上的 1 号插件/剧本（Playbook #1）？** 严禁未经确认直接把后续扩展要复用的通用数据、核心引擎或规则校验底座瘦身删除。
- **三档深度路由**：
  - **L1 明确小工具**：需求已极清晰，不写调研底稿，当轮对齐边界、隐性硬律与不做事项，写 ≤30 行精简 `design/SYSTEM.md`，直接交棒 `bespoke-prototype` / `tech-architect`。
  - **L2 熟悉领域 / 已有系统新增大模块**：跳过基础行业科普与算账，先对齐本次需求边界与领域硬律，再进第一性原理构想与标杆压力测试。
  - **L3 陌生领域新系统（0→1）**：走下面完整的**两段式渐进探索**，允许阶段一多轮追问、边探索边学懂领域。

## 2. 阶段一：问题空间探索（懂规律、补盲区、明需求 · 禁抢推方案）

本阶段只回答“**真实要解决什么问题、守住哪些硬律、绝不做什么**”。**在用户明确确认需求与硬约束已清晰之前，严禁端出完整方案包、严禁贴「推荐」标签替用户选方向、不催促锁骨架**：

1. **意图剥离与单点反向采访**：面对模糊想法或“每天填表/发邮件/点按钮”等既有手工工序，**严禁直接把旧工序翻译成软件**；扮演资深业务分析师**逐轮深挖**，剥离出纯粹的**终极业务结果（Outcome）**、真实前提（使用人数、频率、数据现状、成本上限）与 2–3 条 **Anti-Job**（系统严禁私自越界的红线，含无人值守无事静默）。**提问节奏硬纪律**：默认**每轮只问 1 个最关键问题**（可在开头附 1 行议程路标交代本阶段打算厘清的大方向，让用户有全局感），顺着回答动态追问；仅当两个问题强耦合不可拆时最多合并为 2 个，**严禁问卷式一次连发 3–5 题**。
2. **业内实践第一层前置（揭示领域硬律与未知盲区 Unknown Unknowns）**：当用户不熟悉该领域时，AI 必须主动结合业内实战，用通俗例子讲透该领域的**底层物理/因果规律、高频致命血坑，以及若作为底座服务潜在多下游业务时的前置结构性约束**（帮用户发现“不知道自己不知道”的硬约束——如历史只追加不可篡改与时间线因果一致、关键状态幂等对账、权限与合规审计底线等），由用户自主决定哪些约束须提前埋进底盘。**本阶段刻意屏蔽竞品成品界面与重型架构模板，防止过早锚定。**
3. **轻量探针与动态共识**：可用极轻量的具体场景或反例探针（“如果出现 X 情况，你更希望系统怎样？”）激发用户直觉、暴露隐藏假设；边聊边维护一份简短的**「需求与约束共识」**（Outcome、真实前提、已确认的领域硬律、反目标、Anti-Job），允许多轮发散追问。
4. **显式阶段闸门**：仅当用户明确确认“需求和核心约束已经清楚，可以开始聊方案”时，才进入阶段二。

## 3. 阶段二：解空间探索与收敛（第一性原理先行 → 标杆照妖镜 → 锁 `SYSTEM.md`）

**铁律：业内最佳实践只能作为参考与压力测试，严禁直接照抄套用；具体方案必须从本项目真实需求、资源前提与领域硬律原生推导。**

1. **第一性原理原生构想（先脱壳，禁写 HTML 原型）**：
   - 带着阶段一锁定的需求与领域硬律，抛开既有软件模板，先从第一性原理自由长出 **2–3 种本质不同的原生思路**，讲清各自如何贴合当前实际前提；
   - 交付**“用户的一天”主干流草稿**（标明人做 / 程序做 / AI 做 / 不做，请用户增删），涉及主流程或分区走向时在对话正文附 **10 行级 ASCII 面包板草图**辅助判断。
2. **四源深挖、零凭证探针与“标杆照妖镜”（后校验）**：
   需要外部调研时，优先派子代理执行（当前工具子代理若无外网权限，则由主代理检索并立即落盘 `design/research/<topic>.md` 释放上下文）：
   - **四源交叉查证**：① 官方规则、接口限制与合规红线；② 真实从业者踩坑与耗时卡点；③ 2–3 款代表标杆的真实做法、核心机制与状态流转；④ 单位经济（Unit Economics）与研发/运维成本账。
   - **照妖镜三问（防被标杆带偏）**：引入成品标杆对比时严禁直接套用，必须回答三件事——① **查漏**：标杆多出的复杂设计背后是否藏着我们漏掉的血坑？② **破惯**：标杆哪些设计只是旧时代、大团队或商业卖点的历史包袱，我们应果断扔掉？③ **采珠**：哪些局部机制或数据结构已验证成熟，值得借用？
   - **四级证据打标**：落盘结论必须标注 `[官方文档/实测]`、`[真实界面观察]`、`[从业者复盘]`、`[AI推导-待验]`，严禁把检索摘要包装成确定事实。
   - **隔离只读探针**：遇到公开可测外部数据源/API 字段疑问，允许在 `/tmp`（或会话 scratch 目录）发起**零密钥、零费用、低频公开只读请求**核实真实返回结构；凡需账号密钥、付费或写操作的验证，一律记入切片单的 `Pre-Build Spike`。
3. **单向门收敛 → `SYSTEM.md` v0.1 → 原型回流锁定 v1.0**：
   - **只为单向门出题**（子系统边界、权威数据正本归谁、不可逆安全/合规与底座硬律、主工作流形态）：默认每次只聚焦 **1 个**最关键决定（仅当两项强耦合不可拆时最多合并 2 个），正文讲清贴合本项目实际的真实取舍；**若给出倾向建议，必须同时写明“什么前提下不该选它”**，等用户文字确认（用户回复若附带新疑问，先客观评审收敛，不抢跑）。双向门与底层实现细节直接给合理默认或标“Build 阶段定”。
   - 按 [system-template.md](./references/system-template.md) 写入 `design/SYSTEM.md`（v0.1 候选骨架，控制在 200 行内；单向门推导超 10 条时归档至 `design/decisions.md`）。
   - 转入 `bespoke-prototype`（纯后端/数据跳过）与 `tech-architect`；原型走查暴露的边界问题回到所属子系统修正，同步锁定 `SYSTEM.md` v1.0，并挑出最薄第一片（每天高频用 + 验证最危险假设）。
   - **多模块存量改造收口顺序（先锁总规 → 子代理隔离探针 → 正交拆线）**：若存量改造横跨多条并行开发线，用户拍板宏观决定后必须在 `Mode: design` 下**先落盘锁定 `design/SYSTEM.md` 与 `design/ROADMAP.md`（写清模块独占写目录与波次边界）**，再派独立子代理执行前置真数据/源码探针（`Wave 0`），严禁在未锁总规前把 >5 个底层源码文件读进主会话。
